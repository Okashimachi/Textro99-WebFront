# 08 振り返り

> 得られた知見、次に活かすこと、上流（Docs/Proto/Client-Docs）へ還元すべき候補。

## 知見

- **「表示だけ消す」は、消す範囲の判断が本体だった。** 人間が挙げたのは2か所だったが、実際にバッジが出ていたのは7か所。全文検索で洗い出してから着手したことで消し漏れを防げた。指示の列挙は「気づいた範囲」であって網羅ではない、という前提で読むべき。
- **契約と衝突する要求は、衝突の形を説明してから選ばせるのが早い。** 「数字が打てない」は原因が2つ（入力層のフィルタ / 0-9 の予約）あり、片方は rules/01 §7 に触れる。3案に整理して出したところ1往復で確定した。
- **ラベルと値がズレている表示は、片方を消すと意味が変わる。** `MatchStatusBar` の「撃破」は値がバッジ数だった。単位だけ変えると嘘の表示になるため、タイルごと落とす判断をした（→ [03-判断と決定.md](./03-判断と決定.md) D-3）。
- **非表示化は削除より安い。** テストモードは `?test=1` の1条件で隠せた。コードは残るので、検証手段を失わずに実運用画面だけを整理できる。

## 次に活かすこと

- ブラウザ検証で時間待ちを伴うループを書く前に、`screenshot` を1回撮ってペインを前面に出す（バックグラウンドではタイマーが抑制される）。
- ランダム出題のような非決定な対象を検証するなら、決め打ちできる dev 入口を先に用意したほうが結果的に安い。
