# 07 トークン消費

> 消費量と、その原因／過程。コスト効率の悪い進め方を可視化して次に活かす。

## 概況

| 項目 | 値 |
|---|---|
| モデル | claude-opus-5 |
| セッション数 | 1（log-022 と同一セッションの続き） |
| 規模感 | 中（5件のまとめ修正。新規1ファイル・変更14ファイル） |

## 消費の内訳（定性）

| 過程 | 割合感 | 内容 |
|---|---|---|
| 調査（該当箇所の洗い出し） | 中 | `badge` の全文検索、入力層・romaji・judge の読み込み、画面構成の把握 |
| 方針確認（数字・伸ばし棒） | 小 | 選択肢を3案に整理して人間に確認。**1往復で確定した** |
| 実装 | 中 | 5件を順に適用。typecheck は一発通過 |
| ブラウザ検証 | **大** | 下記の通りロスあり |
| 作業ログ | 中 | 本ログ一式 |

## 効率が悪かった点

1. **ブラウザペインが非表示のとき、`setTimeout` がスロットリングされて検証ループが軒並みタイムアウトした。** 「お題がランダムなので、目的のお題が出るまでボタンを押し続ける」というループを3回書き直した。
   → **原因**: バックグラウンドタブのタイマー抑制。`screenshot` を1回挟んでペインを前面に出したところ、同じコードが一発で通った。
   → **改善案**: ブラウザで時間待ちを伴う検証をする前に、まず `screenshot` を1回撮ってペインを前面にしておく。
2. **`.click()` 直後に同期で DOM を読もうとして失敗した。** React の状態更新が反映される前に読んでいたため、40回ループしても同じ文字列しか取れなかった。
   → **改善案**: クリック後は必ず1フレーム以上待つ（ペインが前面である前提で `await setTimeout`）。
3. **ランダム要素のある検証対象は、そもそも決め打ちできる入口を用意したほうが安い。** 今回は「数字入りのお題」が dev スタブに存在せず、追加してもランダム出題のため引き当てるまでクリックを繰り返す必要があった。

## 効率が良かった点

- **方針が割れる1件だけを先に人間へ確認し、残り4件は確認を挟まず進めた。** 全件について確認を取ると往復が増え、逆に何も聞かずに進めると数字キーの扱いで契約違反の実装を作っていた可能性が高い。
- `badge` の全文検索を最初に一度だけ行い、対象箇所を洗い出してから着手したため、消し漏れの往復が発生しなかった。
