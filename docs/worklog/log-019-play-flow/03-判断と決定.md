## 重要な判断の詳細（ADR 相当）

### 判断 A: 「30秒の猶予」をフロントに実装しない

- **状態 / Status**: 採用
- **日付**: 2026-07-31
- **人間承認**: 済（指示2）

**背景 / Context**

指示1は「部屋作成から試合開始までに30秒の猶予を持たせて下さい」であり、文面上はフロントにタイマーを置く実装にも読める。しかし `MatchmakingStatus.countdownMs` が既に契約にあり、開始判定はサーバー権威（rules/01 §1,§3）。フロントが独自に30秒を数えて開始を決めると、クライアントごとに時計がズレて開始タイミングが揃わない実害も出る。

**決定 / Decision**

フロントは 30 という数値を一切持たない。サーバーが配信する `countdownMs` を残り時間として描画するだけにする。`countdownMs` が来ない間は「人数待ち」表示のまま留まり、ローカルで秒数を数え始めない。

**理由 / Rationale**

- 開始タイミングが全プレイヤーで揃う（サーバーが唯一の時計）。
- 秒数の変更がサーバー設定だけで完結し、フロントの再デプロイが要らない。
- rules/01 §1「戦闘・進行ロジックを JS/TS に書かない」に適合する。

**検討した代替案 / Alternatives**

| 代替案 | 却下・不採用の理由 |
|---|---|
| フロントで30秒カウントし、0で開始扱いにする | 開始判定のクライアント実装。rules/01 §1,§3 に違反し、クライアント間で開始がズレる |
| `countdownMs` 未受信時のみフロントで30秒を仮表示 | 表示とサーバー実挙動が乖離する。ユーザーは「30秒」を信じるが実際の開始は別タイミングになる |

**影響・トレードオフ / Consequences**

- サーバーが `countdownMs` を送らない場合、待機画面は「人数待ち」のまま進行感が出ない。**サーバー側のカウントダウン実装が前提**。
- 逆に秒数の調整（30秒→他の値）はフロント変更なしで反映される。

## 追記（2026-07-31 / 第2次指示）

### 前提の訂正: `countdownMs` はサーバーから送られている

サーバー実装（`internal/matchmaking/matchmaking.go`）を直接読んで確認した事実:

- `MinPlayers: 20` / `MaxPlayers: 99` / `StartCountdownMs: 15000`（`internal/game/params.go` の既定値。**実運用サーバーの保存済み config では MinPlayers=2**）
- 開始条件は「maxPlayers 到達で即開始」または「minPlayers 到達後 startCountdownMs 経過」。カウントダウン中に minPlayers を割ると**リセット**される。
- `broadcast` は参加・離脱のたびに現在値を配信し、カウントダウン中は `countdownMs` に**残り時間ではなく全体秒数**を載せ直す（コード内コメント: 「目安として全体秒数を載せる（クライアントが自前で減算表示）」）。

つまり「カウントダウン用のパラメータが送られていない」わけではなく、**カウントダウン開始後のみ送られ、その値が残り時間ではない**というのが正確な状態。

### 判断 B: 残り秒数を表示せず、イベントログで進行を伝える

- **状態 / Status**: 採用（判断Aの表示部分を**置換**）
- **日付**: 2026-07-31
- **人間承認**: 済（「今後サーバーからカウントダウンを送ってもらうようにするので、今はなにも表示しなくていいです。強いていうならマッチング開始とか人が来たとかのイベント通知は表示するようにして下さい」）

**背景 / Context**

`countdownMs` が全体秒数の再送であるため、`countdownMs - (now - 受信時刻)` で残りを出す既存実装は、**カウントダウン中に誰かが参加するたびに表示が15秒へ巻き戻る**。猶予中に人が入るのが仕様なので実運用でほぼ確実に踏む。フロント側で初回受信時に期限をラッチする回避策も可能だが、サーバーが残り時間を配信する方針が決まったため、暫定表示を作り込まない判断をした。

**決定 / Decision**

残り秒数の表示を削除する。`countdownMs` は**有無だけ**を「カウントダウン中か」の判定に使い、数値は使わない。進行はイベントログ（参加/離脱・カウントダウン開始/中止・試合開始）で伝える。

**理由 / Rationale**

- 誤った秒数を出すより出さない方がよい。巻き戻る数字はプレイヤーの不信を招く。
- サーバーが残り時間を送るようになれば、ラッチのような回避コードを消す手間なく表示を戻せる。

**影響・トレードオフ / Consequences**

- 待機中に「あと何秒か」が分からない。「まもなく開始します」の定性表示のみになる。
- サーバー側で残り時間配信が入ったら、`MatchmakingScreen` に残り秒数表示を戻す（`statusReceivedAtMs` は継ぎ目として props に残してある）。

### 判断 C: イベント生成を reducer に置く（effect ではなく）

- **状態 / Status**: 採用

`main.tsx` が `StrictMode` のため、`useEffect` + `useRef` で前回値と比較する実装は開発時に二重発火してログが重複する。reducer は受信メッセージ1件につき1回しか走らないので、差分の復元と文言生成を `matchmakingEventMessage()` として reducer 側に置いた。既存の `pushEvent`（Welcome/Ko/GameOver）と同じ機構に乗る。
