# 08 振り返り

> 得られた知見、次に活かすこと、上流（Docs/Proto/Client-Docs）へ還元すべき候補。

## 知見

- **「1接続=1試合」の契約下では、離脱は "メッセージを送る" だけでも "接続を切る" だけでも足りない。** 在籍の実体が接続である以上、明示的な離脱通知と切断の両方を、決まった順序で行う必要がある。片方だけの経路が2つ並存していたのが今回の構造的な弱点だった。
- **副作用を useEffect のクリーンアップ任せにすると、意図が読めなくなる。** 「離脱したら切れる」は実際には「stage が変わると effect のクリーンアップが走って切れる」であり、離脱処理を読んでも切断が見えなかった。明示的な操作としてコードに書いたほうが、後から追える。
- **サーバーが見えないバグは、推測より計測が早い。** 最小の WebSocket サーバーを自作して接続数を観測したことで、「クライアントは正しく Leave して切っている」という事実が確定した。これが無ければ、直った確証も、直っていない可能性の説明もできなかった。
- **再現しなかったことは、報告すべき結果である。** 修正前でもローカルでは在籍が 1 に保たれた。この事実を伏せて「直しました」と言うと、実サーバーで再発したときに原因の切り分けが振り出しに戻る。

## 次に活かすこと

- 接続・セッション系のバグは、**コードを読む前に計測器を立てる**。`/probe` のような観測用エンドポイントを1つ持つだけで往復が激減する。
- WebSocket の close を追うときは `WebSocket.prototype.close` にスタック取得のフックを挿す。発生源が一発で分かる。
- ブラウザ検証で時間待ちを伴うなら、先に `screenshot` を撮ってペインを前面に出す（log-023 と同じ教訓）。
