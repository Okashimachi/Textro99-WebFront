# 07 トークン消費

> 消費量と、その原因／過程。コスト効率の悪い進め方を可視化して次に活かす。

## 概況

| 項目 | 値 |
|---|---|
| モデル | claude-opus-5 |
| セッション数 | 1（log-022 / log-023 と同一セッションの続き） |
| 規模感 | 小〜中（変更4ファイル。ただし検証の作り込みが大きい） |

## 消費の内訳（定性）

| 過程 | 割合感 | 内容 |
|---|---|---|
| 原因の絞り込み | **大** | 接続層・App の配線・reducer・画面遷移を横断して読み、離脱経路を洗い出した。仮説を立てては潰す往復が多かった |
| 実装 | 小 | `leaveRoom()` への集約と `@reset` の追加。一発で typecheck 通過 |
| 検証環境の用意 | 中 | `ws` パッケージが無いため、最小の WebSocket サーバーを自作（RFC6455 のフレーム処理を手書き） |
| 検証の実行 | 中 | 修正後 → 修正前（stash）→ 修正後（stash pop）と往復した |
| 作業ログ | 中 | 本ログ一式 |

## 効率が悪かった点

1. **サーバーが見えない状態で原因を推測し続けた。** コードだけを読んで「どこで接続が残るか」を考えたが、決め手が無いまま仮説の数だけ往復した。**先に計測器を作るべきだった**（結果的にそうしたが、順番が逆だと安く済んだ）。
2. **検証中に一度、誤った観測をした。** 「入り直した接続が即座に close された」と読んだが、実際には自分がその後にページ遷移させたことによる close だった。`WebSocket.prototype.close` にスタック取得のフックを挿して初めて発生源が特定できた。
   → **改善案**: 接続まわりの検証では、最初から close のスタックを取る。
3. **ブラウザペインが非表示だとタイマーが抑制される問題を、log-023 で学んだのに再び踏んだ。** `screenshot` を先に撮る手順を徹底できていなかった。

## 効率が良かった点

- **自作の計測サーバーに `/probe` エンドポイントを付けたこと。** 生存接続数・参加者・イベントログを 1 回の `curl` で読めたため、検証の往復が軽くなった。
- **修正前後の比較を `git stash` で行ったこと。** 結果として「再現しない」という重要な事実が分かり、根本原因を断定せずに報告する判断につながった。
