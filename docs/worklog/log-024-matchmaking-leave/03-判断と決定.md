# 03 判断と決定

> AI が下した判断、採用した案・却下した案とその理由、人間の承認。

## D-1: 離脱処理を `leaveRoom()` に集約し、順序を固定した

離脱経路が「Leave を送るだけ」「切るだけ」に分かれていたのを1つにまとめ、**待機列を離れる操作は必ずここを通す**形にした。順序に意味がある。

1. **参加意思を降ろす**（`joinArmedRef = false`）… 以降 open しても `MatchmakingJoin` を送らない
2. **自動再接続を止める**（`setAutoReconnect(false)`）… 切った直後に再接続して再登録されるのを防ぐ
3. **`MatchmakingLeave` を送る**（接続が開いている時だけ）… サーバーが即座に待機列から外せる
4. **接続を切る**（`disconnect()`）… 在籍の実体を消す。close の検知が遅れても 3 で先に外れている

3 と 4 の**両方**を行うのが要点。サーバーがどちらを契機に待機列から外しているか本リポからは分からないため、片方に賭けない。

## D-2: 副作用の実行場所を `net.leave` に寄せた

`ScreenRouter` は `onLeave` で `net.leave()` → `actions.leaveMatchmaking()` の順に呼ぶ既存の構造がある。ここに合わせ、

- `net.leave` = `leaveRoom`（送信・切断・state 初期化）
- `actions.leaveMatchmaking` = 画面の後始末だけ

とした。`ScreenRouter` 側は無変更で済み、送信が二重になることもない。

## D-3: 受信 state を初期化する `@reset` アクションを足した

- 離脱して入り直したとき、新しい `MatchmakingStatus` が届くまで**前のセッションの待機者一覧が表示され続ける**問題があった。これ自体が「自分が複数いるように見える」誤解の一因になり得る。
- S2C とは別種の操作なので、`S2CAction` とは分けた `ResetAction`（`type: "@reset"`）を追加し、`gameReducer` が受けたら `createInitialViewModel()` を返す。
- 却下案: `MatchStart` 時にだけ初期化する。→ マッチング待機中の表示ズレは直らないため不採用。

## D-4: タブを閉じる/リロード時にも `MatchmakingLeave` を送る

- `pagehide` で、接続が開いていれば Leave を送る。
- サーバーが**明示的な Leave を契機に**待機列から外している場合、リロードで抜けたつもりのユーザーが残ってしまうため。close だけに任せない（D-1 と同じ理由）。

## D-5: 根本原因の断定はしていない（重要）

ローカルに検証用の WebSocket サーバーを立てて計測したが、**修正前のコードでも接続数は常に 1 のままで、報告された二重登録を再現できなかった**（→ [06-テスト結果.md](./06-テスト結果.md)）。

- つまり今回の修正は「クライアント側で在籍を曖昧にしていた箇所を塞いだ」ものであり、**実サーバーでの二重登録が本当にこれで消えるかは未確認**。
- サーバーが接続 close を検知するまでにラグがある（ping/pong タイムアウト待ち等）場合、あるいは表示名をキーに登録している場合は、**サーバー側の対応が別途必要**になる。
- この点は報告時に明示し、実サーバーでの確認を依頼する。
