# 02 背景と前提

> このタスクが必要になった理由、参照した上流ドキュメント、前提となる制約。

## 背景

- サーバーは **WebSocket 接続時にのみマッチング登録**する（1接続=1試合）。つまり **待機列の在籍＝接続の生存**であり、接続が残っている限り待機列にも残る。この前提は log-021 で確認済み（`connection.ts` の `reconnect()` コメント）。
- 離脱の経路が2系統に分かれていた。
  - `net.leave()` … `MatchmakingLeave` を送るだけ（切断しない）
  - `exitToTitle()` … 切断するだけ（`MatchmakingLeave` を送らない）
  - 実際の切断は「stage が in-game でなくなったら」という **useEffect のクリーンアップ任せ**で、明示的な操作になっていなかった。
- 加えて、受信 state を初期化する手段が無く、離脱して入り直しても**前のセッションの待機者一覧が残ったまま**表示されていた（新しい `MatchmakingStatus` が届くまでの間）。

## 前提・制約

- proto は変更しない。使えるのは既存の `MatchmakingLeave` のみ。
- サーバー側の実装は本リポからは見えない。**待機列からの除去が「明示的な Leave」と「接続の close」のどちらを契機にしているか不明**なため、どちらでも成立するよう両方を確実に行う方針とした。
- 接続層（`WsConnection`）は薄く保つ。離脱の手順（送ってから切る）はアプリ層（`App`）に置く。
