# 08 振り返り

> うまくいった点・詰まった点・上流ドキュメントに反映すべき知見。

## うまくいった点

- **契約からの削除に型検査が効いた**。`AttackRequest`/`AttackFailed`/`OffsetResolved` を proto から消した結果、依存箇所（入力層・reducer・購読一覧・HUD・モック）が `tsc` で全部炙り出された。vendored な型を正典として素直に使う方針（rules/01 §5,§6）の利点がそのまま出た形。
- **予告どおりの継ぎ目回収ができた**。`deriveRanking()` に「サーバーが rank を配信したら差し替える」とコメントで継ぎ目を明示してあったため、置換が呼び出し側に波及せず局所で済んだ。暫定実装には撤去条件を書き残す運用が機能している。
- ドキュメント（README / rules/01 §7）を同じ PR で更新したので、「操作は3種」という古い記述がコードと乖離したまま残らなかった。

## 詰まった点 / 反省

- **作業ログを着手時に起票していなかった**。実装が未コミットのまま作業ツリーに溜まり、後から差分だけで経緯を復元する羽目になった。01-指示は「記録なし」としか書けていない。
- **ブランチ名と中身が乖離していた**。`feature/hud-console-redesign`（log-017、PR #48 でマージ済み）の上に別テーマの作業を積んでいた。そのままだと PR のタイトルと内容が食い違うため、`feature/proto-v0.1.1` へ切り直した。1 Issue 1 ブランチ（rules/03 §6）から外れていた。
- **ブラウザでの動作確認が未実施のまま PR 化**している。型とビルドは通るが、新規ロジック（予告の自然消滅・`insertIndex` の割り込み）は実行して初めて分かる部類。
- 実サーバーが suspended で結合検証ができず、サーバー側 #77 / #80 との整合が机上のままになっている。

## 別件メモ: WebSocket の 503（PR #49 関連）

本 PR の対象外だが、同セッションで調査したので記録する。

- PR #49（exponential backoff）は意図どおり機能しており、**429 への昇格は解消**。develop / main 双方に反映済み。
- 現在出ている **503 はフロント起因ではない**。`https://textro99-server.onrender.com/` が全パスで即時 503 を返し、レスポンスヘッダが `x-render-routing: suspend`、本文が "This service has been suspended."。**コールドスタート（スピンダウン）ではなくサービス停止**で、コードでは解決できない。Render 側の再開が必要。
- 調査中、4リクエストを連続で投げた時点で Render のエッジが 429 を返した。**エッジ側のレートリミットは健在**なので backoff は引き続き必要。
- 残っているフロント側の弱点（別 Issue 候補）:
  1. 再接続に**ジッタが無い**。全クライアントが同時に切断され足並みを揃えて再試行するため、復旧時に thundering herd になりエッジの 429 を誘発しうる。
  2. **無限リトライ・ユーザーへの説明なし**。30秒間隔で永久に再試行し、画面には生の英語ステータス `reconnecting` が出るだけ。打ち切りと手動再試行の導線が無い。
  3. ブラウザの WebSocket API は upgrade 失敗時の HTTP ステータスを露出しないため、コード側で 503 を識別できない（`fetch` プローブなら判別可能）。
