## 重要な判断の詳細（ADR 相当）

### 判断 A: 試合中順位をサーバー確定値のみに一本化する

- **状態 / Status**: 採用（log-008 期の「近似順位」判断を**置換**）
- **日付**: 2026-07-31
- **人間承認**: 不要（rules/01 の原則に沿った是正のため）

**背景 / Context**

`src/state/ranking.ts` の旧 `deriveRanking()` は、プロトコルが順位を配信していなかった時期の暫定実装で、生存 → バッジ数 → コンボ → スタック数 の優先度でクライアントが独自に順位を組み立てていた。これは rules/01 §1「戦闘ロジックを JS/TS に書かない」§3「表示は受信 state ベース」に抵触する状態で、当時のコメントにも「サーバーが rank を配信するようになったらこの関数を差し替える」と継ぎ目が明記されていた。proto v0.1.1（server #80）で `PlayerSummary.rank` が入り、その条件が満たされた。

**決定 / Decision**

`deriveRanking()` を削除し、`sortByServerRank()` に置換する。クライアントは順位の決定に一切関与せず、サーバー値の昇順に並べ替えるだけとする。呼び出し側のシグネチャ（`players`, `selfPlayerId` → `RankedPlayer[]`）は変えない。

**理由 / Rationale**

- 順位の正典がサーバーに一本化され、クライアント表示とサーバー確定順位の食い違い（旧実装では不可避）が消える。
- 予告どおりの継ぎ目回収であり、呼び出し側を変えずに差し替えられる。

**検討した代替案 / Alternatives**

| 代替案 | 却下・不採用の理由 |
|---|---|
| 近似算出を残し `rank` 未配信時のフォールバックにする | 順位のソースが二重化し、どちらが正典か実行時まで分からなくなる。rules/01 §3 に反する |
| `rank` 未確定の間だけ近似を使う | 同上。「一瞬だけクライアント順位」が出て、確定時に順位が飛ぶ体験になる |

**影響・トレードオフ / Consequences**

- サーバーが `rank` を送らない／0 のままだと、順位表示は playerId 順のフラットな並びになる。**サーバー側 #80 の実装が前提**。
- 関数名が変わるため、`deriveRanking` を参照している箇所は追従が必要（本 PR 内で対応済み）。
