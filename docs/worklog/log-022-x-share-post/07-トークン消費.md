# 07 トークン消費

> 消費量と、その原因／過程。コスト効率の悪い進め方を可視化して次に活かす。

## 概況

| 項目 | 値 |
|---|---|
| モデル | claude-opus-5 |
| セッション数 | 1 |
| 規模感 | 小（新規3ファイル・変更4ファイル。実装そのものは軽量） |

## 消費の内訳（定性）

| 過程 | 割合感 | 内容 |
|---|---|---|
| 壁打ち（設計判断・フォーマット案出し） | 中 | フロント／バックの切り分け、投稿フォーマット3案の提示。**実装前に方針を固めたぶん、手戻りはゼロ**だった |
| ルール・既存コードの読み込み | 中 | `docs/rules/01,02`、`ResultActions` / `MatchResultScreen` / `ResultBoard` / `Panel` / `proto/types.ts` |
| 実装 | 小 | 新規3ファイル＋差分4ファイル。一発で typecheck 通過 |
| ブラウザ検証 | **大（想定外）** | 下記の通り、ブラウザ操作でロスが出た |
| 作業ログ・PR 作成 | 中 | 本ログ一式 |

## 効率が悪かった点

1. **dev サーバーのポート不一致でロスした。** 別セッションの dev サーバーが 5173 を占有しており、Vite が 5174 にフォールバックした一方、プレビュー用ツールは別ポートを見ていた。空ページのスクリーンショットや失敗ナビゲーションを数回繰り返した。
   → **改善案**: 起動直後に `preview_logs` で Vite が実際に出した URL を確認してから操作を始める。
2. **UI をクリックで辿るのが高コストだった。** タイトル → テスト用 → 練習 → 名前入力 → デバッグペイン展開 → モック注入、という多段のクリックで、`read_page` / `screenshot` を往復した。座標のズレやクリック不発でさらに往復が増えた。
   → **改善案**: 検証対象が「特定の state での描画」なら、最初から `javascript_tool` で目的のボタンを直接 `click()` し、`title` 属性等を読んで検証する。今回もこの方式に切り替えた時点で一気に解決した。

## 効率が良かった点

- **実装前に壁打ちを挟んだこと**（指示 #1, #2）。方針・文面が確定済みだったので、実装フェーズでの書き直しが発生しなかった。
- ボタンの `title` に投稿本文をそのまま入れた設計が、そのまま検証手段になった（DOM から1発で文面を読める）。
