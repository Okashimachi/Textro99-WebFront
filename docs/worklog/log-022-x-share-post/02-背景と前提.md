# 02 背景と前提

> このタスクが必要になった理由、参照した上流ドキュメント、前提となる制約。

## 背景

- log-021 でリザルトが決着画面（`MatchResultScreen`）として整い、操作ブロック（`ResultActions`）に「再マッチング / タイトルへ」が並んだ。ここに結果の SNS 共有導線を足したい、という要望。
- 投稿テキストの正典は**最終的にサーバー**に置く方針が人間から示されている（指示 #3）。よって今回のクライアント実装は暫定であり、**捨てやすさ＝差し替え地点の明確さ**が設計上の主要因になる。
- 事前の壁打ち（指示 #1, #2）で、フロント／バックの切り分けと投稿フォーマットの案出しを済ませてから実装に入った。

## 前提・制約

- **X API（`POST /2/tweets`）はクライアントから叩けない。** OAuth のトークンが必要で、フロントに置けばバンドルに秘密情報が載る（rules/02 §4 に抵触）。API 方式を採るなら必然的にサーバー実装になる。
- proto に共有テキスト用のフィールドが無いため、サーバー配信へ移行するには **Proto 側の契約追加（人間承認フロー）が先に必要**。今回はそこに手を付けない。
- 共有文面の組み立ては「確定値の文字列整形」に留める。順位・撃破数を数え直す、勝敗を判定し直す等は行わない（rules/01 §1, §3）。
