# 03 判断と決定

> AI が下した判断、採用した案・却下した案とその理由、人間の承認。

## D-1: X API ではなく Web Intent 方式を採用（指示との差分あり）

指示 #3 は「XのAPIを叩いて」だったが、**Web Intent（`https://x.com/intent/post`）** で実装した。

- **理由**: X API のツイート投稿は OAuth トークンが必須。トークンをフロントに置くとバンドルに秘密情報が載り、rules/02 §4 に抵触する。API 方式は必然的にサーバー実装になり、「フロントにモックを置く」という指示 #3 の前半と両立しない。
- **要件は満たせる**: 「ポストする直前まで」＝ 本文入りの投稿画面が開き、確定はユーザーが押す状態。Web Intent はこれそのもの。
- **副次的な利点**: 認証もトークン管理も不要なので、本番（Unity/unityroom）でも `Application.OpenURL` で同じ URL を叩けば流用できる。
- 実装報告時に人間へ明示済み。

## D-2: 共有テキストの生成を `src/share/shareText.ts` の1か所に閉じた

将来サーバー配信になる前提なので、**捨てる範囲を1ファイルに固定**した。

- `ShareText { text, url }` という型を挟み、UI（`ResultActions`）はこの型だけを受け取る。
- 差し替え手順（Proto 拡張 → 呼び出し元の置換 → 文面組み立ての削除）をファイル冒頭のコメントに明記した。
- これにより、サーバー配信へ移行しても **UI 側は無変更**で済む。

## D-3: 共有文面に「正確率」を入れなかった

- 正確率は `ResultBoard` が表示用に割り算している値（log-011 と同じ「表示計算」の扱い）。共有文面にも入れると**同じ計算を2か所に持つ**ことになる。
- 文面がサーバー配信へ移る前提なら、正確率もそのとき一緒にサーバー側で載せるのが筋。よって今回は `rank` / `koCount` / `maxCombo` の3値のみを使った。

## D-4: 順位帯ごとの文面出し分けを実装しなかった（却下案）

壁打ち段階で「1位 / 2〜3位 / 4〜10位 / …」で文面を変える案（案B）を提示したが、**優勝かどうかの分岐のみ**に留めた。

- 文面はサーバーの担当になる予定であり、モック段階で作り込むと丸ごと捨てる作業になる。
- 優勝時だけは達成感の差が大きいので、最小限の分岐として残した。

## D-5: 文字数（重み280）のバリデーションを入れなかった（却下案）

- X の文字数計算（日本語=2、URL=一律23）を実装すると、それ自体が「サーバーが担保すべきルール」をクライアントに置くことになる。
- 未使用のヘルパーを増やしても死にコードになるため、今回は入れない。

## D-6: 共有先 URL を環境変数 `VITE_SHARE_URL` にした

- rules/02 §4（接続先 URL をコードに直書きしない）に揃えた。公開先が未定でも、未設定なら URL なしで共有される形にして動くようにした。
